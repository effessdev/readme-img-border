Border for GitHub READMEs

Adds a border that still looks right after GitHub shrinks a wide image down to fit the page.

How it works

Open any section below for the details.

Why GitHub shrinks your image

GitHub's markdown CSS gives every image a max-width: 100% rule. The README content column is roughly 838px wide, so any image wider than that is scaled down by the browser to fit the column. The image on disk is never changed — the shrink happens at render time, and the scale factor is simply the image's natural width divided by 838. A 1676px-wide image is shown at 50% size, a 2514px image at 33%, and so on. Images narrower than the breakpoint render at full size and are not touched at all.

The problem with a fixed-pixel border

This scaling is the root of the problem. If you add a 1px border in an image editor and the image is later shrunk to 50%, that border is rendered at half a pixel once GitHub displays it — thin, blurry, and inconsistent with whatever else is on the page. Add a thicker border to compensate and it will be wrong again the moment the image is narrower than the column, or the moment GitHub's layout changes. There is no single pixel value that works everywhere, because the correct value depends on how much the image will be scaled.

How the border thickness is calculated

This tool solves that by working in the opposite direction. It takes the image's natural width, compares it to the 838px breakpoint, and computes the scale factor GitHub will apply. It then multiplies the desired on-screen border thickness (1px by default, set by MIN_WIDTH) by that same factor and rounds to a whole number of pixels. A 1676px image gets a 2px baked-in border; once GitHub shrinks the image by half, that border reads as exactly 1px. A 3352px image gets a 4px border, which also reads as 1px after the 4× shrink. The border in the file is bigger than what you see — but only by exactly the amount GitHub is about to take away.

How the output image is built

The output image is the source image plus the border on all four sides, so the final canvas is the source width plus twice the border by the source height plus twice the border. The border is drawn first as a filled rounded rectangle spanning the whole canvas, then the source image is clipped to an inner rounded rectangle and drawn on top. The outer corner radius is scaled up by the same factor as the border so it also reads correctly after shrinking, and the inner radius is the outer radius minus the border thickness, which keeps the border itself an even width all the way around the corners. With the default radius of 0 this reduces to square corners, but the geometry is already in place if you want rounded ones.

How the border color is chosen

The border color is chosen in one of three ways. Light and Dark simply use the two colors defined in the config (LIGHT_COLOR is a dark slate, DARK_COLOR is a light grey — the names describe the image they suit, not the border itself). Auto, the default, samples the image to decide which of the two will be more visible. The image is drawn into a tiny 32×32 offscreen canvas (AUTO_SAMPLE_SIZE) so the sampling is fast regardless of how large the source is, and the average perceived brightness of every pixel is computed using the standard luma weights (0.299 red, 0.587 green, 0.114 blue). Pixels that are almost fully transparent — alpha below AUTO_ALPHA_CUTOFF, 16 by default — are skipped, so a PNG with a lot of transparent padding doesn't get mistaken for a bright image just because most of its pixels are empty. If the average brightness is above AUTO_LUMINANCE_THRESHOLD (128, i.e. mid-grey), the image is treated as light and gets the dark border; otherwise it gets the light border. If the canvas can't be read at all — which happens with cross-origin images that taint the canvas — the code falls back to treating the image as light and using the dark border, on the assumption that a visible border is better than no border.

What the readout and buttons do

Under the preview you'll see a readout like 1676×942 source → 1680×946 output · border 2px (scaled 2.00x so it reads as 1px once GitHub shrinks it to fit). The left side is the image you loaded; the right side is the PNG this tool will produce. The border figure is the raw pixel count baked into that PNG, and the parenthetical tells you whether scaling was applied at all — for an image narrower than 838px it will say no scaling was needed, and the border will simply be 1px. Nothing is uploaded anywhere: the whole pipeline runs in your browser on a canvas, and Download saves the result as a PNG while Copy puts it on the clipboard for pasting straight into a GitHub issue or README editor.
